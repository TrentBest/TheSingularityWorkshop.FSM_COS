# FSM_COS 0.1.0-alpha.7 — Release Readiness Gate

**Purpose:** this is the single release-gate definition for alpha.7. It is deliberately not a running diary of every earlier CI run. Use GitHub Actions and the exact artifact as evidence; do not copy old results forward.

## Candidate identity

- **Package:** `TheSingularityWorkshop.FSM_COS`
- **Version declared by the project:** `0.1.0-alpha.7`
- **Integration branch:** `development`
- **Publication:** not authorized by this checklist. A successful build or package artifact does not publish a release.
- **Evidence rule:** every CI result and package inspection is valid only for the exact source commit that produced it. The final candidate is the `development` HEAD for which required CI passed and whose package artifact was inspected. Any subsequent source change invalidates that final-candidate designation until reverified.

## Current implementation contract to preserve

The code and tests, not this checklist, define the behavior. The alpha.7 candidate hardens the versioned-root manifest and immutable collection surfaces. In particular:

- Root requests carry a MicroBundle ID and requested version; conflicting versions for the same root identity must fail before loading.
- FSM_COS resolves domain-owned MicroBundles through the catalog, loads dependencies before dependents, then arbitrates to convergence with a bounded round count.
- Optional schedule/load-plan data is validated against the resolved graph before bundle loading. It is planning metadata, not a repository localization engine or an independent process scheduler.
- Configuration comes from the optional configuration-source boundary, not inline manifest payloads.
- The returned RuntimeAssembly is a handoff object. FSM_COS does not execute the host application, present UI, persist state, transport artifacts, or manage host lifecycle.
- Read-only collections do not make MicroBundle instances themselves immutable.
- Exceptions from relevant catalog, configuration, load, and arbitration callbacks propagate; do not imply rollback of side effects already performed by a bundle.

For detailed behavior, use [Architecture](ARCHITECTURE.md), [Runtime Manifest](RUNTIME_MANIFEST.md), [Staged Manifest Loading](STAGED_MANIFEST_LOADING.md), [Consuming MicroBundles](CONSUMING_MICROBUNDLES.md), and [RuntimeAssembly](RUNTIME_ASSEMBLY.md). This list is a guardrail, not a substitute for those contracts.

## Release gates

### A. Source and contract

- [ ] Review public API and XML documentation against implementation and tests.
- [ ] Verify root-version precedence, dependency closure/order, staged-plan consistency, duplicate/missing IDs, cycles, resolution/version failures, and pre-load rejection.
- [ ] Verify load/configuration/arbitration exceptions and non-convergence behavior, including the documented limits on rollback and diagnostics.
- [ ] Confirm deferred capabilities are clearly labeled as deferred in every public-facing explanation and diagram.

### B. Repository and CI

- [ ] Confirm `development` is the intended release source and inspect the exact HEAD SHA.
- [ ] On that SHA, pass `build-and-test`, `public-package-compatibility`, and `source-integration`.
- [ ] Confirm the package-verification paths pass and the publish job remains skipped unless the owner explicitly authorizes publishing.
- [ ] Review warnings, test output, workflow configuration, and package workflow inputs—not just the overall green badge.

### C. Exact package

- [ ] Download the `.nupkg` generated by the successful run for the exact candidate SHA.
- [ ] Verify package ID/version, repository commit metadata, target framework, direct dependency versions, license, package README, XML docs, required documentation and visual assets, and exclusions for internal planning files.
- [ ] Run the repository package verifier and independently inspect the package archive.
- [ ] Record the exact workflow run, artifact name, package SHA-256, and source SHA in the release review outside this mutable checklist. Do not copy hashes from an earlier candidate.
- [ ] Confirm the public NuGet feed still reports the previous version until publication actually succeeds.

### D. Documentation and accessibility

- [ ] Resolve any mismatch between source, tests, package metadata, root README, NuGet README, release notes, focused contract guides, and the documentation index.
- [ ] Check links, filenames, examples, API names, dependency versions, implementation status, and package inclusion/exclusion rules against the current tree.
- [ ] Check SVG source semantics and alt text. Treat hosted rendering, browser accessibility-tree exposure, keyboard behavior, and screen-reader behavior as separate checks; do not claim them verified without direct evidence.
- [ ] Ensure the index points readers to one primary authority per concern and that historical planning documents are not presented as current specifications.

### E. Publication authorization and post-publish verification

- [ ] Obtain explicit owner approval for publication.
- [ ] Deliberately dispatch `.github/workflows/package.yml` from `development` with the required `publish` input set to `true`. Do not enable publication as a side effect of ordinary CI.
- [ ] Verify the publish job succeeded and the exact version appears on NuGet.
- [ ] Record the published version, source SHA, workflow run, package URL, and package hash.
- [ ] Recheck that publication is not unintentionally enabled for future pushes.

## Explicitly outside alpha.7

These are not alpha.7 promises: repository localization/content-byte verification; asynchronous or background localization; bootstrap-only initial composition; live promotion of deferred bundles into an existing RuntimeAssembly; automatic application execution; UI/presentation; persistence; transport; host lifecycle management; and immutability of MicroBundle objects themselves.

A capability enters scope only when its owner, contract, failure behavior, compatibility rules, and minimum verification evidence are defined and implemented.

## Status calculation

Readiness is **100% only when all applicable gates above are evidenced for one exact candidate SHA**, documentation and package agree with the source, no known release blocker remains, and any external verification claims are honestly bounded. Publication authorization is a separate decision.

The latest Actions run and its artifacts are the evidence source for the current candidate. This document intentionally does not embed a second, easily stale copy of run IDs or package hashes. If the latest successful run's SHA differs from the current `development` HEAD, or its exact package artifact has not been inspected, the exact-candidate gates remain open.
